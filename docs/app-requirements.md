# App Requirements — BookShelf

## 1. Призначення
BookShelf — невеликий локальний вебзастосунок для ведення особистої бібліотеки. Один користувач може обліковувати книги, знаходити їх у каталозі та фіксувати статус читання без реєстрації чи зовнішніх сервісів.

## 2. Обґрунтування вибору
Предметна область зрозуміла, обсяг обмежений, результати перевіряються конкретними сценаріями CRUD, пошуку та зміни статусів. Python, Streamlit, SQLite і pytest дозволяють створити прототип у межах навчального курсу без платної інфраструктури.

## 3. Функціональні вимоги
| ID | Вимога | Критерій приймання |
| --- | --- | --- |
| FR-01 | Додавати книгу з назвою, автором та необов'язковим описом | Запис зберігається і відображається у каталозі |
| FR-02 | Переглядати каталог | Усі збережені записи доступні після повторного запуску |
| FR-03 | Редагувати книгу | Зміни зберігаються в SQLite |
| FR-04 | Видаляти книгу | Перед видаленням користувач отримує підтвердження |
| FR-05 | Шукати за назвою чи автором | Результати відповідають введеному фрагменту тексту |
| FR-06 | Змінювати статус читання | Доступні рівно три стани: «Планую прочитати», «Читаю», «Прочитано» |
| FR-07 | Зберігати дані між сеансами | Після перезапуску застосунку дані не втрачаються |

## 4. Нефункціональні вимоги
- Україномовний і зрозумілий інтерфейс.
- Локальна робота без обов'язкового підключення до Інтернету.
- Перевірка обов'язкових полів і зрозумілі повідомлення про помилки.
- SQLite без окремого сервера бази даних.
- Модульна структура, яка дозволяє тестувати бізнес-логіку незалежно від UI.
- Документовані залежності й інструкція запуску.

## 5. Технологічний стек
- **Python** — бізнес-логіка та доступ до даних.
- **Streamlit** — вебінтерфейс.
- **SQLite** — локальне зберігання книг.
- **pytest** — автоматизовані перевірки.
- **Git/GitHub** — історія змін і спільний доступ до результатів.

## 6. Агентна IDE
**VS Code + Codex CLI.** Вибір обґрунтований роботою з локальним кодом, можливістю агенту виконувати обмежені завдання розробки й тести, а також переглядом diff перед прийняттям змін. Людина залишається відповідальною за вимоги, дозволи та фінальне прийняття результату.

## 7. Межі першої версії
Не плануються багатокористувацький режим, авторизація, хмарна синхронізація, рекомендаційна система, зовнішні книжкові API та мобільний застосунок. Вони не потрібні для перевірки основних сценаріїв.

## 8. Перевірка результату
Приймання передбачає ручну перевірку основних сценаріїв інтерфейсу та автоматизовані тести операцій створення, читання, редагування, видалення, пошуку й зміни статусу. Конкретні тести будуть реалізовані в наступних практичних роботах.
