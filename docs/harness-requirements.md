# Harness Requirements — BookShelf

## 1. Мета
Agent harness — інженерна інфраструктура навколо Codex CLI, яка забезпечує керований доступ до контексту, правил, інструментів і перевірок. Harness **не є** користувацьким інтерфейсом BookShelf та не замінює відповідальність розробника.

## 2. Джерела даних
| Джерело | Вміст | Спосіб використання |
| --- | --- | --- |
| Репозиторій BookShelf | Код, README, вимоги, конфігурація | Локальне читання агентом у межах робочої директорії |
| Git-історія та GitHub | Коміти, зміни, задачі за наявності | Git-команди; надалі GitHub MCP |
| Результати pytest | Статус тестів, повідомлення про помилки | Запуск тестів і аналіз виводу |
| CI/CD (після налаштування) | Результати автоматичних перевірок | GitHub / інтеграція за наявності |
| BookShelf-KB | Поняття, рішення, компоненти, глосарій | **Тільки через визначений MCP-конектор**, без прямого доступу до vault |

## 3. Цільові задачі агента
1. **Реалізація функцій:** створювати невеликі модулі та елементи інтерфейсу за узгодженими вимогами; цінність — швидше отримання перевірюваного інкременту.
2. **Генерація тестів:** писати й запускати pytest-тести CRUD, пошуку та статусів; цінність — раннє виявлення регресій.
3. **Перевірка відповідності:** порівнювати зміни з документованими вимогами й правилами; цінність — зменшення розбіжностей між завданням і реалізацією.
4. **Діагностика помилок:** аналізувати трасування, локалізувати дефекти й пропонувати мінімальні виправлення; цінність — скорочення часу налагодження.
5. **Оновлення знань:** документувати підтверджені архітектурні рішення у BookShelf-KB через MCP; цінність — збереження контексту для наступних завдань.

## 4. Первинні категорії guardrails
Це категорії на рівні задуму, **не реалізовані правила**. Деталізація й технічне забезпечення передбачені в ПР4.

| Категорія | Приклади дій |
| --- | --- |
| **allow** | Читання файлів BookShelf; перегляд Git diff/status; запуск локальних тестів; підготовка змін у межах погодженого завдання |
| **warn** | Зміна залежностей; міграція схеми SQLite; масове редагування; коміт або push; запис у базу знань через MCP — після перегляду людиною |
| **block** | Видалення репозиторію чи його історії; force-push у main; розкриття секретів; доступ до файлів поза дозволеним робочим простором; пряме читання/редагування BookShelf-KB в обхід MCP |

## 5. Цільова архітектура
1. **Agent/IDE:** Codex CLI у VS Code отримує обмежене завдання.
2. **Data sources:** локальні файли, Git, тести, надалі CI/GitHub.
3. **Knowledge layer:** окремий Git-репозиторій BookShelf-KB (Obsidian vault).
4. **MCP connectors:** контрольований інтерфейс до бази знань і GitHub.
5. **Guardrails:** категорії allow/warn/block та перевірки перед небезпечними діями.
6. **Skills:** повторювані інструкції для тестування, рев'ю та документування.
7. **Orchestration:** послідовність «аналіз → план → зміни → тести → рев'ю → документація».
8. **Evaluation:** результати тестів, відповідність вимогам і дотримання обмежень.

## 6. Межі автономності й контроль
Агент може пропонувати та виконувати дозволені локальні операції, але не ухвалює самостійно архітектурних рішень із великим впливом. Зміни з категорії warn потребують погодження, а block — не виконуються. Після кожного завдання розробник переглядає diff і результати перевірок.

## 7. Поетапне впровадження
- **ПР1:** вимоги до застосунку та harness (цей документ).
- **ПР2:** структура знань в Obsidian.
- **ПР3:** MCP-конектори.
- **ПР4:** деталізація guardrails.
- **ПР5:** skills.
- **ПР6:** orchestration.
- **ПР7:** RAG та evaluation.

На момент ПР1 перелічені компоненти є **планом**, а не твердженням про вже реалізовану інфраструктуру.
